# Northwing 0.3 Work-first Product Design

**Status:** Approved for implementation by the Northwing 0.3 product brief
**Target version:** 0.3.0
**Target branch:** `agent/northwing-0.3-work-first-shell`
**Product promise:** From intent to finished work.

## 1. Outcome

Northwing 0.3 is a Work-first CoWork desktop product. It opens on a product Home surface, makes New Work the dominant action, presents Projects, Work, and Artifacts as primary objects, and retains Quick Chat as a secondary path for informal tasks.

The execution stack remains the existing Reasonix-derived kernel. Northwing adds product and domain projections around that kernel. It does not add a second planner, executor, agent loop, tool runtime, permission engine, checkpoint engine, or recovery engine.

The target architecture is:

```text
Northwing Product Shell
        ↓
Northwing Work Experience
        ↓
Northwing Domain
        ↓
Reasonix-derived Kernel
```

The product shell owns navigation, Home, Projects, Work, Artifacts, New Work, Quick Chat positioning, settings entry points, brand, update UX, and release identity. The Northwing domain owns Work policy, Work lifecycle projection, acceptance, materials, artifacts, versions, migration, and the Harness v3 contract. The kernel continues to own providers, models, sessions, Goal, planner, executor, subagents, Skills, MCP, tools, permissions, approvals, checkpoints, recovery, memory, terminal, Git, remote workbench, automations, and bots.

## 2. Baseline findings

The 0.2 implementation contains useful CoWork foundations and several structural gaps that define the 0.3 work.

- `internal/agent/branch.go` persists session metadata in `<session>.jsonl.meta`, yet `BranchMeta` has no Work identity.
- `desktop/tabs.go` exposes `TabMeta` and `ProjectNode`, while `desktop/app.go` exposes `SessionMeta`; none contains `sessionKind` or `workId`.
- `desktop/frontend/src/components/ReasonixProjectTree.tsx` reads all CoWork summaries and joins WorkRef records to native rows by `goalId` or `sessionPath`.
- `desktop/frontend/src/components/NorthwingWorkSessionSurface.tsx` repeats the same lookup for the active tab and renders a narrow Work strip over the chat surface.
- `desktop/frontend/src/lib/northwingCowork.ts` saves WorkRef before the first provider request, which preserves a useful ordering guarantee, yet it never writes native session identity.
- Backend Work stage values and frontend Work stage values represent different concepts under the same name. The backend stores coarse lifecycle stages; the frontend type lists Harness steps.
- `App.tsx` is a 5,300-line controller and render hub. It always enters a session surface and has no Home destination.
- Current Northwing UI checks rely heavily on source-file regular expressions. Browser behavior is not covered.
- The Northwing release workflow publishes an empty `signature` field, does not publish a detached manifest signature, does not Authenticode-sign the three Windows executables, and contains no `signtool verify /pa /all` gate.
- The silent NSIS update path waits briefly and then runs `taskkill /F`.

These findings were independently mapped against the committed baseline at `8f42d658dce362c0a5351dca3f52897203969825`.

## 3. Considered implementation shapes

### 3.1 Selected: native session identity plus a product shell adapter

This shape adds Work identity to the existing session sidecar, projects it through tabs, history, and the project tree, and places a lazy Northwing product shell above the current session workspace. The current transcript, composer, approvals, asks, reasoning, tools, runtime, and workbench remain reusable session primitives.

Advantages:

- one session runtime and one execution authority;
- restart-safe Work routing without a project-manifest scan;
- incremental migration with narrow persistence changes;
- a distinct product experience without risky package renames;
- realistic delivery within the existing Wails and React architecture.

### 3.2 Rejected: a second Work runtime

This shape would introduce a Work coordinator that plans, executes, pauses, repairs, and resumes independently from the existing controller. It would duplicate critical kernel behavior and create conflicting sources of execution truth.

### 3.3 Rejected: a visual overlay on the current chat shell

This shape would keep the existing sidebar and chat layout and add more Work bars, drawers, and menu actions. It would preserve the product hierarchy that 0.3 is required to replace and would continue loading the session UI on the Home path.

## 4. Native SessionKind contract

### 4.1 Canonical persisted fields

The durable session authority is `agent.BranchMeta`, stored beside the transcript. It gains:

```go
type SessionKind string

const (
    SessionKindChat SessionKind = "chat"
    SessionKindWork SessionKind = "work"
)

type BranchMeta struct {
    // existing fields
    SessionKind SessionKind `json:"session_kind,omitempty"`
    WorkID      string      `json:"work_id,omitempty"`
}
```

The public Wails and frontend contract is:

```ts
export type SessionKind = "chat" | "work";

export type NativeSessionIdentity = {
  sessionKind: SessionKind;
  workId?: string;
};
```

Missing legacy `session_kind` normalizes to `chat` at read boundaries. New session creation writes `chat` explicitly. A Work identity is valid only when `sessionKind=work` and `workId` is a valid Northwing Work ID. A chat identity never carries a Work ID.

`SessionMeta.Kind`, currently used for external channel transcripts, remains a transport/source classification. It is not reused for Work identity. Channel sessions receive `sessionKind=chat` when no native Work identity exists.

### 4.2 Kernel API

The agent package exposes validation and atomic sidecar mutation:

```go
func NormalizeSessionKind(kind SessionKind) SessionKind
func ValidateSessionIdentity(kind SessionKind, workID string) error
func SetSessionIdentity(sessionPath string, kind SessionKind, workID string) error
func LoadSessionIdentity(sessionPath string) (SessionKind, string, error)
```

The desktop exposes a kind-aware creation path:

```go
func (a *App) EnsureWorkTab(workspaceRoot, workID string) (TabMeta, error)
```

`EnsureWorkTab` creates or safely reuses a blank project tab, validates that it has no transcript content, writes `sessionKind=work` and `workId` to the sidecar, updates the in-memory tab, and returns metadata only after the write succeeds. Work launch calls this method before WorkRef persistence and before `SubmitInitialGoalToTab`.

Existing `EnsureBlankTab` remains the ordinary session path and always yields `sessionKind=chat`. Its blank-reuse predicate rejects blank Work sessions. A fresh session rotation resets identity to chat. Recovery branches and conflict-adoption branches inherit the source session identity because they remain continuations of the same Work. Manual Convert to Work creates a separate Work session and leaves the source chat identity unchanged.

### 4.3 Projection surfaces

The following structures expose `sessionKind` and `workId` directly:

- `WorkspaceTab` and `TabMeta`;
- `agent.SessionInfo` and desktop `SessionMeta`;
- `ProjectNode` for topic and session leaves;
- frontend `TabMeta`, `SessionMeta`, and `ProjectNode`.

Project-tree builders and history listing read the session sidecar as their authority. Work policy may be joined by `workId` after the native identity is known. UI code must not scan every WorkRef to decide whether a session is Work.

## 5. Northwing 0.2 to 0.3 migration

### 5.1 Manifest schema

`.northwing/project.json` advances from schema version 2 to 3. Version 3 keeps project policy and index data:

- Work ID and title;
- session link;
- Work type, quality, source policy, model, effort, and pause policy;
- materials, expected artifact, audience, constraints, and acceptance items;
- Harness version and ordered Harness steps;
- lifecycle projection and unresolved findings;
- artifacts, versions, hashes, validation state, and final selection link.

It does not define whether a session is Work. That fact lives in `BranchMeta`.

WorkRef gains a migration-visible binding state:

```go
type WorkBindingStatus string

const (
    WorkBindingNative      WorkBindingStatus = "native"
    WorkBindingNeedsRebind WorkBindingStatus = "needs_rebind"
)
```

`bindingStatus` communicates a recoverable migration result. It never substitutes for `BranchMeta.session_kind`.

### 5.2 Safe resolver

For each 0.2 WorkRef, migration resolves a native session in this order:

1. Load the explicit `sessionPath` when it points to an existing transcript owned by the same project workspace.
2. Require existing sidecar scope and workspace fields to agree when they are present.
3. Require the sidecar topic ID to agree with `goalId` when both values are present.
4. If the explicit path is unavailable, search the project session index for an exact `TopicID == goalId` match.
5. Accept the topic fallback only when exactly one session matches.

The resolver never chooses by title, modification time, model, transcript content, or approximate path. A conflicting existing `work_id`, multiple topic matches, missing transcript, workspace mismatch, or topic mismatch produces `bindingStatus=needs_rebind`. The original WorkRef remains available and the UI displays “Needs session rebind.”

### 5.3 Idempotency and integrity

The first schema-2 migration writes the original bytes once to `.northwing/project.v2.backup.json`. Project writes remain atomic. Native sidecar writes are idempotent: a matching Work identity is a no-op; a conflicting Work ID is an error.

The migration preserves these values exactly:

- Work ID;
- transcript bytes and event-log bytes;
- artifact SHA-256, version, size, path, and creation time;
- `final-artifacts.json` selection;
- model binding and reasoning effort;
- quality and source policy;
- existing Work title and session/topic links.

Repeated migration must leave project.json, final-artifacts.json, transcript files, and native metadata unchanged after the first successful pass. A failed schema write leaves the original manifest intact and returns the existing read-only fallback. A failed native bind keeps the manifest usable with `needs_rebind`.

### 5.4 Migration trigger

Migration runs through the Northwing desktop domain adapter whenever a project is loaded for Home, Projects, Work, Artifacts, or direct Work open. This guarantees normal startup and deep-open paths converge. `internal/cowork` owns schema normalization; the desktop adapter owns the session-directory and BranchMeta binding because it already knows project session locations.

## 6. Harness v3 and lifecycle projection

### 6.1 Separate enums

The user-visible lifecycle is:

```ts
export type WorkStage =
  | "intake"
  | "planning"
  | "producing"
  | "reviewing"
  | "repairing"
  | "validating"
  | "waiting_user"
  | "completed"
  | "failed";
```

The internal policy sequence is:

```ts
export type HarnessStep =
  | "inspect"
  | "inventory"
  | "evidence_ledger"
  | "plan"
  | "produce"
  | "review"
  | "independent_review"
  | "repair"
  | "validate"
  | "requirement_audit";
```

Quality plans are fixed:

| Quality | Harness steps |
| --- | --- |
| Quick | inspect → produce → validate |
| Standard | inventory → plan → produce → review → repair → validate |
| Deep | inventory → evidence_ledger → plan → produce → review → independent_review → repair → validate → requirement_audit |

Step-to-stage projection is fixed:

| Harness step | Work stage |
| --- | --- |
| inspect, inventory, evidence_ledger | intake |
| plan | planning |
| produce | producing |
| review, independent_review | reviewing |
| repair | repairing |
| validate, requirement_audit | validating |

### 6.2 Work Contract v3

The first Work submission contains one normal user task with these ordered sections:

1. Goal
2. Work type
3. Inputs
4. Materials
5. Expected artifact
6. Source policy
7. Constraints
8. Acceptance
9. Execution policy
10. Internal Harness steps

The contract contains domain and execution policy. It avoids component names, CSS, routes, panels, and other UI implementation details. Work metadata is excluded from the stable system prompt and enters once through the initial user task.

Harness v3 asks the kernel to record observable progress through the existing workflow tools. Harness todos use the exact prefix `[harness:<step>]`; acceptance todos use `[acceptance:<id>]`. These tags form an internal projection protocol and are removed from user-facing labels.

### 6.3 WorkCoordinator projection

`NorthwingWorkCoordinator` is a pure adapter. It consumes existing evidence and emits a Work projection:

```ts
type WorkRuntimeEvidence = {
  goalStatus?: string;
  running: boolean;
  pendingApproval: boolean;
  pendingAsk: boolean;
  startupError?: string;
  canonicalTodos: Todo[];
  latestTool?: { name: string; args?: string; success?: boolean };
  turnLifecycle?: "idle" | "started" | "done";
};

type WorkProjection = {
  stage: WorkStage;
  harnessStep?: HarnessStep;
  acceptance: AcceptanceItem[];
  unresolvedFindings: string[];
};
```

Projection precedence is deterministic:

1. startup/runtime failure → `failed`;
2. approval, ask, blocked Goal, clarification, scope decision, or missing input → `waiting_user`;
3. completed Goal with all acceptance items complete → `completed`;
4. first incomplete tagged Harness todo → mapped stage;
5. current tagged Harness todo → mapped stage;
6. a running turn with no tagged evidence keeps the last durable stage;
7. a fresh Work with no evidence starts at `intake` for Quick and `planning` only when its first Harness step maps there.

Timers never advance Work. Elapsed time is display data only. The coordinator does not submit prompts, execute tools, retry models, or change permissions.

## 7. Product shell and navigation

### 7.1 Shell boundary

The frontend gains `desktop/frontend/src/northwing/` with focused modules:

```text
northwing/
  Shell/
  Home/
  Projects/
  Work/
  Artifacts/
  Navigation/
  DesignSystem/
  QuickChat/
  NewWork/
  domain/
  testing/
```

`NorthwingShell` owns product destinations and lazily opens the session workspace. It stays small enough that Home does not import `useController`, Transcript, Composer, Office preview, terminal, Git diff, settings, Skills, MCP, Automation, or developer tools.

The current session controller surface moves behind a lazy `SessionWorkspace`. `App.tsx` becomes a compatibility entry that mounts the new shell and provides session actions. It no longer owns product navigation markup.

### 7.2 Destinations

Primary navigation order:

```text
Northwing logo
+ New Work
Home
Projects
Work
Artifacts

Automations
Skills
MCP

Models & Accounts
Settings

Quick Chat
Advanced tools
```

Terminal, Git changed files, remote workbench, commands, and developer controls remain available through Advanced tools, command palette, and context actions. They do not occupy default primary visual positions.

### 7.3 Navigation persistence

The first launch and every launch without an explicit resumable destination opens Home. A Work workspace stores a compact local destination containing `workId` and project root. Reload validates the native session identity and returns to that Work. A stale destination falls back to Home with a recoverable notice.

Home can coexist with a dormant active kernel tab. Visiting Home does not create, rotate, or submit a session.

## 8. Product pages

### 8.1 Home

Home displays:

- a dominant New Work call to action;
- Continue working cards with Work title, project, stage, acceptance progress, and updated time;
- Waiting for you cards for approval, clarification, scope decisions, and missing input;
- Recent artifacts with final state, type, Work, project, and updated time;
- Recent projects;
- a smaller Quick Chat action.

Home reads a cheap catalog projection. It does not sync artifact directories or load session history on first paint.

### 8.2 Projects

The Projects destination lists recent projects and opens a project page containing:

- project header and New Work action;
- Materials;
- Works as the main region;
- recent outputs;
- Chats as a secondary region.

Work rows support text search, stage filter, waiting/completed/in-progress categories, and updated-time sorting.

### 8.3 Work Workspace

The desktop Work workspace uses a three-column layout with a fixed header and instruction composer:

```text
┌────────────────────────────────────────────────────┐
│ Work title · project        Stage · Acceptance     │
│ Type · Quality · Source policy · Executor model   │
├──────────────┬────────────────────────┬────────────┤
│ Work Plan    │ Activity              │ Materials  │
│ Stage        │ Transcript            │ Artifacts  │
│ Harness      │ Reasoning / Tools     │ Versions   │
│ Acceptance   │ Approval / Ask        │ Final      │
│ Findings     │                       │            │
├──────────────┴────────────────────────┴────────────┤
│ Instruction composer                              │
└────────────────────────────────────────────────────┘
```

The center reuses existing Transcript, Composer, approval, ask, reasoning, tool-event, and runtime state. The Work layout owns their placement and visual hierarchy. The active tab routes here only through `activeTab.sessionKind === "work"`.

The left plan shows current WorkStage, ordered Harness steps, acceptance items, and unresolved findings. The right panel has Materials, Artifacts, and Versions tabs. Artifact actions cover preview, open, reveal, revise, mark final, and history.

### 8.4 New Work

New Work is available from Home, Project, Work list, and command palette. Project entry preselects its project. Home entry first selects an existing project or a new folder.

The default form asks:

- What do you want to finish?
- Materials
- Output type
- Quality
- Source policy
- Model

Audience, constraints, acceptance overrides, pause policy, and reasoning effort live in an Advanced disclosure. Focus is trapped inside the dialog, Escape closes it, the triggering element regains focus, validation errors use `role=alert`, and submission order is observable in tests.

### 8.5 Quick Chat and Convert to Work

Quick Chat creates or opens `sessionKind=chat`. It shows the existing conversation and composer without Work plan, acceptance, materials, artifacts, versions, or final-output regions.

Convert to Work is an explicit action. It derives a draft objective from the chat title and existing user messages, opens the New Work confirmation form, and creates a separate Work session. The original transcript remains unchanged. Conversion completes only after user confirmation.

### 8.6 Global Artifacts

The global Artifacts page reads an aggregate backend catalog without triggering full artifact rescan. Filters cover Project, Work, file type, final only, and updated time. Selecting an artifact opens its Work and activates the artifact context. Northwing does not add a standalone document editor.

## 9. Artifact and Office contracts

Formal outputs remain under `deliverables/<work-id>/`. Existing SHA-256 dedupe and append-only version assignment remain authoritative.

Artifact metadata gains validation state and update time while preserving the current identity fields:

```go
type Artifact struct {
    ID               string
    Path             string
    Kind             string
    WorkID           string
    Version          int
    SHA256           string
    Size             int64
    CreatedAt        time.Time
    UpdatedAt        time.Time
    ValidationStatus string

```

The `northwing_office` tool and DOCX, PPTX, XLSX, and PDF create/inspect/validate/revise capabilities remain kernel tools. A successful turn completion triggers bounded artifact sync for the active Work. The Work panel immediately displays type, version, validation status, updated time, and final badge.

## 10. Brand and design system

### 10.1 Brand boundary

Ordinary Northwing UI text must not contain “Reasonix.” This includes navigation, onboarding, composer, settings descriptions, dialogs, update surfaces, errors, crash surfaces, theme authorship shown to users, and browser mocks.

Allowed occurrences are confined to About, licenses, third-party attribution, and developer documentation, using the statement “Northwing is derived from / powered by the Reasonix kernel baseline.” Internal Go package names, protocol identifiers, CSS class names, storage keys, and source comments may retain the legacy name when they are not rendered.

A shared `productizeUserText` function converts inherited kernel error text at the presentation boundary. Locale strings use Northwing directly. The brand audit mounts ordinary routes and settings surfaces and inspects rendered DOM text; it excludes only explicitly marked About/legal roots.

## 12. Windows release security

### 12.1 One release signing credential

Formal Windows release consumes one protected GitHub Environment secret named `NORTHWING_WINDOWS_RELEASE_CREDENTIAL`. Its JSON payload contains the base64 PFX and password for the Northwing Authenticode certificate. PR and ordinary CI jobs never receive it.

The same certificate private key signs the detached update manifest signature. The release build extracts the certificate SubjectPublicKeyInfo and injects it into `northwing.exe` through a linker variable. This keeps one external signing credential and gives the updater a pinned verification key. Certificate rotation requires publishing the next public key in an earlier trusted release.

### 12.2 Authenticode chain

The release job performs this sequence:

1. import the PFX into an ephemeral runner certificate store;
2. build `northwing.exe` with the pinned manifest public key;
3. build `northwing-update-helper.exe`;
4. sign both binaries with SHA-256 Authenticode and an RFC3161 timestamp;
5. run `signtool verify /pa /all` on both binaries;
6. package the signed binaries into setup and portable artifacts;
7. sign setup.exe with the same policy;
8. run `signtool verify /pa /all` on setup.exe;
9. create checksums and the update manifest from the signed outputs;
10. create `northwing-update.json.sig` as a detached SHA-256 certificate-key signature;
11. verify the detached signature through the same Go verifier shipped in Northwing;
12. publish only after every verification succeeds.

Missing or malformed release credentials fail the formal release job before publication. Pull requests may upload clearly named unsigned test artifacts with short retention. They cannot create a GitHub Release.

### 12.3 Signed manifest

The manifest schema is strict and versioned:

```json
{
  "schemaVersion": 1,
  "product": "Northwing",
  "version": "0.3.0",
  "channel": "stable",
  "publishedAt": "2026-08-07T00:00:00Z",
  "repository": "owner/repository",
  "releaseNotes": "https://github.com/owner/repository/releases/tag/northwing-v0.3.0",
  "assets": {
    "windows-x64": {
      "name": "Northwing-0.3.0-windows-x64-setup.exe",
      "url": "https://github.com/owner/repository/releases/download/northwing-v0.3.0/Northwing-0.3.0-windows-x64-setup.exe",
      "sha256": "64 lowercase hexadecimal characters",
      "size": 1
    }
  }
}
```

The updater trust order is immutable:

```text
download bounded manifest bytes and detached signature
→ verify detached signature against the pinned key
→ parse strict JSON
→ validate product, channel, version, repository, filename, size, and HTTPS URL
→ download the selected setup
→ verify exact size and SHA-256
→ verify Authenticode on Windows
→ launch the verified helper
```

An empty signature, unknown field, foreign host, unexpected repository, unsupported schema, rollback version, checksum mismatch, untrusted Authenticode signature, or oversized response fails closed.

### 12.4 Graceful update handoff

Normal update flow:

```text
Northwing downloads and verifies
→ Northwing verifies the installed helper
→ helper starts with current PID and canonical paths
→ Northwing snapshots and exits normally
→ helper waits for the exact PID
→ timeout aborts with no installer launch
→ helper launches installer with a deadline
→ installer replaces files only while Northwing is absent
→ helper verifies installed Authenticode and `northwing version`
→ helper restarts Northwing
```

NSIS contains no forced-kill command. Silent helper mode aborts when Northwing is running. Manual mode displays a close-and-retry prompt. The installer has no Ignore-and-overwrite path for `northwing.exe`.

### 12.5 Repository identity

Runtime identity lives in one Go module and is linker-overridable for formal builds. Workflow URLs use `${{ github.repository }}` and release metadata. Frontend opens release pages through a backend-provided URL. A controlled list of historical repository paths supports GitHub rename redirects without scattering repository literals.

## 13. Testing strategy

### 13.1 Deterministic unit and contract tests

- session identity validation, persistence, rotation, recovery inheritance, and projection;
- v2-to-v3 project migration, native binding, ambiguous binding, conflict handling, protected-field equality, and repeated-run byte stability;
- WorkStage/HarnessStep mapping and evidence projection precedence;
- Harness v3 normalization and contract compilation;
- artifact version, hash, validation state, and final selection preservation;
- manifest strict parsing, signature verification, URL trust, checksum, rollback, and size limits;
- helper wait timeout, installer timeout, version mismatch, and restart arguments;
- installer source contract rejecting `/F`, Ignore, and overwrite while running;
- brand presentation adapter and Northwing-visible copy.

### 13.2 Rendered component tests

JSDOM tests click and type through Navigation, New Work, Project filters, Work/Chat router, artifact actions, focus trap, Escape, and error handling. Source contract checks remain for generated bindings and packaging invariants; they do not count as UI completion evidence.

### 13.3 Playwright acceptance

Chromium runs at 1440×900 against Vite with the controllable browser Wails bridge. It covers the complete acceptance path:

1. startup opens Home;
2. Home shows New Work;
3. create a project;
4. open New Work;
5. enter the goal;
6. select Work type;
7. create Work;
8. enter Work Workspace;
9. observe `data-session-kind=work`;
10. observe Stage;
11. observe Acceptance;
12. observe Materials;
13. inject and observe an Artifact;
14. mark it final;
15. close the page;
16. reload the app;
17. return to the same Work;
18. retain Work and artifact state;
19. create Quick Chat with `sessionKind=chat`;
20. confirm Work acceptance UI is absent.

Additional tests cover keyboard navigation, DOM brand audit, chunk requests, error states, and Convert to Work confirmation. Reviewed screenshots cover Home, Project, Work Workspace, and New Work. Screenshots support visual review and do not replace assertions.

### 13.4 Windows acceptance

Windows CI continues portable, installer, CLI version, GUI startup, `northwing://`, uninstall, and overwrite coverage. It adds the real helper handoff, graceful old-process exit, installed-version validation, restart, signature verification, signed manifest verification, and explicit absence of forced-kill behavior.

## 14. Release gates

Required local and CI gates:

- frontend typecheck, complete test suite, production build, bundle budget, and Playwright;
- root `go test ./...`;
- desktop `go test ./...`;
- Go formatting and `git diff --check`;
- migration fixtures;
- brand DOM audit;
- Windows Wails build and packaging E2E;
- Authenticode and manifest-signature verification in formal release mode;
- CodeQL and Northwing CI.

The implementation branch opens one PR against `main-v2`. The PR is not force-merged. The `northwing-v0.3.0` tag is created only after merge, green main-v2 validation, green Windows and UI E2E, green migration, and verified signatures. If `NORTHWING_WINDOWS_RELEASE_CREDENTIAL` is absent, the result stops at release-ready and reports that one external credential requirement.

## 15. Compatibility and failure behavior

- Existing Reasonix-derived kernel packages keep their current import paths.
- Existing mature capabilities remain reachable through the new shell and Advanced tools.
- Existing chats normalize to chat without transcript rewrites.
- Existing Work policy and artifacts remain accessible when native binding needs repair.
- Missing optional Work data renders explicit recoverable states; it does not silently hide Work.
- A stale shell destination returns Home.
- A failed artifact sync keeps the prior artifact catalog and shows a retry action.
- A failed update verification never launches an executable.
- A helper timeout leaves the installed version unchanged.

## 16. Design self-review result

The design defines one session authority, one runtime, one migration resolver, separate lifecycle enums, exact UI boundaries, the release trust chain, credential boundary, test paths, compatibility behavior, and failure behavior. Every required migration field and release gate has an owner. The selected design contains no unresolved interface decision that blocks implementation.
